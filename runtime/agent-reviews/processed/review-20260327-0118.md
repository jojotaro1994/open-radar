## Repo State Summary

Tasks 1-2 (architecture artifacts + core ontology scaffolding) are marked DONE. All 9 object types and their filesystem-backed JSON stores exist. The canonical local-folder layout helper (`intelligence-layout.ts`) correctly maps Evidence, Finding, DecisionObject, etc. to `intelligence/topics/{topic}/{collection}/{id}.json` and review/learning objects to `review/{collection}/{id}.json`.

**Runtime integration is partial.** `run-pipeline.ts` creates Evidence (from scored signals), Findings (for approved signals), and DecisionObjects (from assembled opportunities). CLI exposes `/decisions`, `/findings`, `/evidence`, and `/review decision <id>`. This means the core read path works for the middle of the chain.

**Critical gaps:** The ends of the chain (ReferenceFact, ActionAsset) are not used. The governance layer (HumanReviewFeedback, EvidenceRequest) has read-only CLI display but no write path. The learning loop (RetrospectiveCase, LearningMemory) is entirely inert. Meeting governance still operates on raw signals, not DecisionObjects.

20 files are modified with ~1700 lines of uncommitted changes.

## Findings (ordered by severity)

### HIGH

**f1 — HumanReviewFeedback has no write path**
`feedbackStore.save()` is never called anywhere. CLI reads feedback for display in `/review decision <id>` and `/review feedback`, but no command or runtime flow creates feedback objects. The structured feedback loop specified in Task 5 is entirely scaffolding.

**f2 — EvidenceRequest has no write path**
Same pattern as f1. Store exists, CLI displays requests in `/review decision <id>`, but `evidenceRequestStore.save()` is never called.

**f3 — Meeting governance still centered on raw signals, not DecisionObjects**
`evaluateWithMeetingRoom()` in `ba-meeting-room.ts` takes `signalId` and `CommercialAssessment`, not `DecisionObject`. MeetingRecord is produced per-signal during triage (run-pipeline.ts line 437), BEFORE DecisionObjects are even created (line 498). The design requires meeting to govern DecisionObjects, but the current implementation structurally prevents this due to temporal ordering.

**f4 — RetrospectiveCase and LearningMemory are completely inert**
Stores are imported in CLI but never instantiated as variables. No code creates, reads, or lists these objects. Tasks 5-6 have zero runtime implementation.

### MEDIUM

**f5 — ActionAsset and ReferenceFact stores are unused**
Neither store is imported or used in any orchestrator, CLI, or engine file. These represent the start and end of the `ReferenceFact -> Evidence -> Finding -> DecisionObject -> ActionAsset` chain, and both extremes are passive type definitions only.

**f6 — Metrics (ARR/NRR/NDR) are always undefined at runtime**
`DecisionObject.metricsImpact` is hardcoded to `undefined`. `Finding.metricsContext` attempts to read `assessment.arrImpact` etc., but these fields do not exist on `CommercialAssessment`. Task 8 cannot be verified.

**f7 — ReviewQueue.triage() still uses free-text reason**
All 12 runner files plus `run-pipeline.ts` call `reviewQueue.triage(signalId, decision, reviewedBy, reason?)` with a plain string. This old interface has not been migrated toward structured feedback.

**f8 — Pipeline ordering prevents DecisionObject-centered meeting**
`run-pipeline.ts` creates MeetingRecord during triage (Step 5), before DecisionObjects are created (Step 7b). This temporal ordering makes it structurally impossible for meeting to govern DecisionObjects without pipeline reordering.

### LOW

**f9 — No tests for new object model**
`invariants.test.ts` only tests old review-queue and signal invariants. No test verifies Evidence/Finding/DecisionObject creation, lineage backlinks, or store persistence.

**f10 — Uncommitted changes touch a different OpenSpec change**
`recenter-cli-radar-copilot/proposal.md` and `tasks.md` are modified in the unstaged diff alongside intelligence-operating-model work. Verify this is intentional cross-change sync.

## Recommended Next Focus

1. **Reorder the pipeline.** Move DecisionObject creation upstream so it happens before meeting evaluation. Then migrate `evaluateWithMeetingRoom` to accept `DecisionObject + Finding bundle` instead of `signalId`. This unlocks Task 4.

2. **Add a HumanReviewFeedback write path.** Implement a CLI command (e.g. `/review submit <decisionObjectId> <resolution> <feedbackClass> [reason]`) that creates and persists structured feedback. This makes Task 5 real.

3. **Add one integration test** that verifies Evidence -> Finding -> DecisionObject lineage persistence and confirms backlink IDs resolve to actual objects.
