## Findings (ordered by severity)

### HIGH

**f1 — EvidenceRequest write path still absent**

`evidenceRequests: []` is hardcoded at radar-cli.ts:1197. The `onApply` callback destructures `_requests` but never calls `evidenceRequestStore.save()`. The type, store, and CLI display are all in place — only the persistence call is missing.

```
src/cli/radar-cli.ts:1197  evidenceRequests: []
src/cli/radar-cli.ts:1198  onApply: (feedback, _requests) => { feedbackStore.save(feedback) }
```

**Recommendation:** Extend the `/review decision <id>` command to accept one or more evidence request entries before confirming. Persist via `evidenceRequestStore.save()` inside `onApply`.

---

**f2 — Pipeline ordering still prevents DecisionObject-centered meeting governance**

`run-pipeline.ts` creates MeetingRecord via `evaluateWithMeetingRoom(signal.id, ...)` at lines 437-445, before DecisionObjects are created at line 495. `ba-meeting-room.ts` still takes `signalId` not `DecisionObject`. This is the structural blocker for Task 4.

**Recommendation:** Reorder the pipeline. Create DecisionObjects first (Step 7b), then run meeting evaluation as a second pass over DecisionObject bundles. Keep the legacy MeetingRecord path for backward compatibility during the transition.
